---
title: Why Frasto
description: The interface-library gap Frasto is designed to close for Astro teams.
---

Astro is excellent at shipping fast, content-rich websites. Teams building more interactive interfaces still need a coherent set of controls, feedback, navigation, data display, and layout components that preserve Astro's server-first strengths.

## The missing middle

Browser primitives are powerful but deliberately unstyled. Framework-heavy UI kits often assume a persistent client runtime. Copy-pasted snippets leave accessibility, states, visual consistency, and upgrades to each project.

Frasto occupies the useful middle:

```text
Native web platform
Semantic HTML / CSS / forms
        ↓
Frasto UI
Components / tokens / documented contracts
        ↓
Real interfaces
Marketing / commerce / content / products / operations
```

## Why Astro first

An Astro interface should not need to become a client-rendered application to use a serious component library. Frasto starts with useful server-rendered HTML and CSS, then introduces focused behavior only when interaction requires it.

## Why breadth and quality both matter

A small primitive set is easy to start and difficult to finish. Frasto aims for broad coverage while holding every component to the same standard: clear APIs, complete states, accessibility, responsive behavior, and composability.

## Why patterns still matter

Components solve recurring units of interface work. Patterns show how those units cooperate across tasks such as navigation, search, filtering, forms, settings, dashboards, and resource workflows. They are reusable guidance, not a required application framework.

## Positioning

Frasto is not a port of a React library and is not “shadcn for Astro.” It is an open-source Astro-first component library and design system intended to become dependable across many kinds of websites and applications.

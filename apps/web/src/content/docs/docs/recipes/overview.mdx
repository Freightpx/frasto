Recipes are production-shaped examples, not isolated component galleries. They use concrete content, believable data density, responsive layouts, dark mode, and complete data states.

## What recipes validate

- component APIs compose without awkward adapters
- page hierarchy remains clear across routes
- application density feels practical
- loading, empty, error, and partial states are coherent
- keyboard and touch interaction work across components
- light and dark themes feel like one product
- missing components become visible before release

## Data policy

Initial recipes use mock TypeScript data. A database is unnecessary for validating presentation contracts and application patterns.

## Planned recipe families

SaaS, CRM, CMS, ERP/inventory, admin, and customer portal examples may follow. They should reuse the same system rather than introduce separate visual languages.

## First recipe

[Acme Cloud](/docs/recipes/acme-cloud/) is the initial end-to-end SaaS application used to pressure-test Frasto.

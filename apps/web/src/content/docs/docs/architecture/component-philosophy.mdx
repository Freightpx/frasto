---
title: Component philosophy
description: Design component APIs around intent and repeatable application problems.
---

## Do not wrap HTML without adding a system

A component should provide meaningful consistency, behavior, semantics, composition, or application vocabulary. A component that only renames one HTML element is usually unnecessary.

## Prefer semantic APIs

Good:

```astro
<Button variant="solid" tone="danger" size="sm">
  Delete
</Button>
```

Avoid APIs that expose visual implementation as a bag of utility values.

## Separate presentation and meaning

A useful vocabulary is:

- `variant` → presentation treatment
- `tone` → semantic meaning
- `size` → physical scale
- `state` → interaction/data condition

## Application components matter

The project is differentiated by higher-level components such as:

- AppShell
- PageHeader
- ResourceTable
- FilterBar
- DetailLayout
- SettingsLayout
- ActivityFeed

These are not templates pasted on top of unrelated primitives. They should follow the same tokens and interaction rules.

## Composition before configuration

Prefer slots and small cooperating components when a single prop-heavy component would need to anticipate every application. Configuration is appropriate for structured data such as columns and options; authored content often composes more clearly.

## State is public behavior

Loading, empty, invalid, disabled, selected, and error states belong in the specification. A component API is incomplete if consumers must inspect source to understand those states.

## Do not own the application

Components may express interaction intent, but the application controls routing, persistence, authorization, fetching, and business rules.
